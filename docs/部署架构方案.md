# 部署架构方案：CI 构建 + 服务器零构建

> 状态：已实现（第一期）。第二期（统一 Caddy 入口、多项目共用 80/443）待做。
> 相关仓：`deploy-kit`（本仓，发布中枢）· `xuexu`（第一个接入方）

---

## 0. 结论

服务器不构建。CI 在 GitHub Actions 上构建前端产物和后端镜像，传到服务器，
由 `deploy-kit` 的发布器原子切换 + 健康检查 + 失败自动回滚。

改造前服务器 2C / 1.9 GiB / 39G(用 11G)，`npm run build` 实测峰值 **1.19 GiB**
而 available 只有 1.3 GiB —— 每次发前端都在 OOM 边缘。

---

## 1. 事实依据（实测，不是推测）

### 1.1 服务器现状

| 项 | 实测值 |
|---|---|
| 根分区 | 39G，已用 11G（28%），可用 27G |
| Docker | `/var/lib/docker` 771M；镜像 883MB；构建缓存 324MB |
| 内存 | total 1.9Gi / used 582Mi / **available 1.3Gi** / swap 4Gi |
| CPU | 2 核 |
| Node | v22.22.1（**原来没有任何版本钉死机制**） |
| `/opt/learning/repo` | 302M（含 node_modules 约 280M） |

### 1.2 构建的资源占用

| 构建 | 峰值内存 | 位置 |
|---|---|---|
| `npm run build`（tsc + vite） | **1,278,459,904 B = 1.19 GiB** | macOS 实测，`/usr/bin/time -l` |
| `docker build`（api 镜像） | 镜身体积 61 MB | 迁移时已在 1.9 GiB 服务器上成功构建过 |

> 结论：后端镜像在服务器上构建**可行**（有 layer cache、体积小）；
> 前端构建**不可行**（1.19 GiB vs available 1.3 GiB）。
> 但既然已经搬了 CI，后端一起搬更干净 —— 前后端版本永远同一个 sha。

### 1.3 空间不是瓶颈

两个项目（xuexu + kids-english-copilot）全部部署完约 **2 GB / 39 GB（5%）**。
`backup.sh` 有 `KEEP_DAYS=14` 保留策略，备份目录有上限。
**真正的瓶颈是内存，不是磁盘。**

## 2. 架构

```text
开发机 push
   │
   ▼
GitHub Actions（deploy-kit 的 reusable workflow）
   │  ① npm ci && npm run build  → tar.gz（约 2-5 MB）
   │  ② docker build → docker save | gzip（约 25 MB）
   │  ③ scp 传到服务器（受限 deploy key）
   │  ④ ssh 触发发布
   ▼
服务器（deploy-kit）
   releaser.sh apply <项目> <sha>
     ├ 解包前端 → releases/web/<sha>/
     ├ docker load → 打 tag <image>:current
     ├ 换**目录**替换 deploy/web（换 inode）
     ├ 重建 api/worker + caddy
     ├ 健康检查 → 不过就自动回滚
     └ 记版本、清理旧版本（留最近 3 个）
```

---

## 3. 关键决策

### 3.1 传输用 scp，不用 rsync

用户最初选的是 rsync over SSH。实现时发现：`authorized_keys` 的 `command=`
会**顶掉** SSH 客户端请求的远程命令，而 rsync 依赖远程执行
`rsync --server <一堆参数>`，这些参数很难严格校验后原样 exec。

scp 只有一个 `scp -t <目标路径>`，目标路径可以精确校验成
`<项目产物目录>/<sha>.{web-dist,api-image}.tar.gz` → 校验通过后原样 exec。

**校验不通过就拒绝**，一条都上传不进去。

### 3.2 后端镜像用固定 tag，不用 sha 插值

`image: xuexu-api:current`，发布时 `docker tag xuexu-api:<sha> xuexu-api:current`。

如果 compose 里写 `image: ${VAR:-xuexu-api:<sha>}`，那么**每一次** `docker compose up`
都必须记得传环境变量，漏一次就静默回退到旧镜像 —— 这种坑不值得踩。
固定 tag 让 compose 文件永远自洽。

回滚时把旧 sha 的镜像重新打成 `current` 即可（本地旧镜像一直留着）。

### 3.3 前端换**目录**而不是换文件

Caddy 的 bind mount（`./web:/srv/web:ro`）在**容器创建时**就解析了源目录的 inode。
改目录里的文件不生效，必须换整个目录 + 重建 caddy 容器。

这是沿用 xuexu 原有 `auto-deploy.sh` 里已经验证过的做法，没有引入新风险。

### 3.4 服务器保留本地构建兜底

`auto-deploy.sh` 三条路径：

| 路径 | 触发条件 | 说明 |
|---|---|---|
| ① CI 产物 | 产物已到服务器 | 主路径，服务器不构建 |
| ② 本地构建 | 没有 CI 产物 | 原有行为，应急用 |
| ③ `--no-local` | 显式指定 | 纯 CI 模式（服务器清掉 node_modules 后） |

保留 ② 是为了**不把退路堵死**：CI 挂了还能手动发一次版。

### 3.5 密钥与项目绑定（多项目场景下的必要条件）

`authorized_keys` 的强制命令写成：

```
command="/opt/deploy-kit/push-incoming.sh --project xuexu",restrict ssh-ed25519 ...
```

`push-incoming.sh` 据此把**这把密钥焊死在一个项目上**：只能往该项目的产物目录上传、
只能发布/查询该项目，**没绑定的密钥一律拒**（没有逃生口）。

⚠️ 这是多项目彩排（T9）实测出来的漏洞：原实现里 `scp` 分支遍历**所有**项目的
注册表找匹配目录，`apply` 也接受任意项目名 —— 等于 **kids 的 CI 密钥能往 xuexu 的
产物目录里塞文件、也能触发 xuexu 的发布**。一台服务器上跑多个项目时，
这是一条现成的横向越权通道。

### 3.6 包管理器不写死（npm / pnpm / yarn）

`reusable workflow` 原来写死 `npm ci` + `package-lock.json`。
实测 kids-english-copilot 用的是 **pnpm**（`pnpm-lock.yaml`，lockfileVersion 5.4），
没有 `package-lock.json` → `setup-node` 的缓存步骤会**直接失败**，CI 一步都跑不动。

改成 `package_manager` 输入（默认 npm），装依赖前先检查锁文件在不在，
缺了直接报「找不到锁文件 xxx」，而不是让 setup-node 抛一句看不懂的错。
pnpm 的**大版本从项目自己的锁文件推断**（v5.4→pnpm7 / v6.0→pnpm8 / v9.0→pnpm9）——
不在 workflow 里另配一份版本，免得和项目脱节。

> 这条不只是 kids 的问题 ——「以后还会有其它项目想发版」，
> 下一个项目用 pnpm/yarn 就直接踩同一个坑。

### 3.7 锁分离

- 定时器锁 `/run/learning-deploy.lock` —— 防定时器自己重叠
- 发布锁 `/run/deploy-<项目>.lock` —— 防 CI 触发的发布和本地构建同时改 `deploy/web`

本地构建期间占住发布锁，CI 的发布会快速失败并重试（workflow 里重试 5 次）。

## 4. 第二期（待做）：统一 Caddy 入口

现在每个项目自己独占 80/443，第二个项目没法再占。

**方案 C（最干净）**：把 Caddy 抽成独立的 `gateway` compose 项目，统管所有域名，
各项目加入一个 `external` 的共享网络（`edge`），gateway 反代到各项目 api：

```caddyfile
xuexu.43.129.21.98.sslip.io {
    reverse_proxy xuexu-api:8002
}
kids.43.129.21.98.sslip.io {
    reverse_proxy kids-api:8002
}
```

⚠️ **风险最高的一步**：要迁 `learning_caddy_data` / `learning_caddy_config`
两个证书卷（不迁就要重新签发证书），计划停机约 15 秒，必须先本地彩排再上。

第一期不做，等第二个项目真正要上线时再做。

## 5. 踩坑记录

| 坑 | 现象 | 修法 |
|---|---|---|
| `command=` 顶掉 rsync | rsync 连不上 | 改用 scp，路径严格校验后 exec |
| `$var` 后紧跟非 ASCII | UTF-8 locale 下 `unbound variable` | 一律 `${var}`，T0 静态守卫永久拦截 |
| `local a=1 b=$a` | 同句里 `$a` 在赋值前就被展开 | 拆成两行 |
| `"$X"; true` | `;` 不保护 set -e，前一条失败脚本就死 | 改 `\|\| true` |
| `LOCK_DIR` 是死代码 | 配了环境变量不生效 | 统一用 `${LOCK_DIR}` |
| 写死 `/root/.ssh` | sudo 保留原用户 HOME 时公钥写错地方 | 取 `getent passwd 0` 的家目录 |
| 脏检查只排除 `data/` | `deploy/web/` 一旦被 git 跟踪，每次发布后工作区就脏 → 定时器全拒跑 | 显式排除 `deploy/web/` |
| 注册表多词值没加引号 | `HEALTH_SERVICES=api caddy` 被 `.`（source）时，`caddy` 被当成命令执行 → exit 127 | 生成时加引号；彩排真 source 一次验 |
| scp 分支遍历所有项目 | **kids 的 CI 密钥能往 xuexu 的目录塞文件、能触发 xuexu 发布** | 密钥与项目绑定（§3.5） |
| 安装脚本自检没带 `--project` | 自检把自己判成失败 → `install-server.sh` 退出码非 0 | 自检也带 `--project` |
| reusable workflow 写死 `npm ci` | 用 pnpm 的项目（`pnpm-lock.yaml`，没有 `package-lock.json`）→ `setup-node` 缓存步骤直接失败 | 加 `package_manager` 输入；pnpm 大版本从锁文件推断（§3.8） |
| 同一个 step 写了两条 `if` | GitHub 报 `Invalid workflow file ... 'if' is already defined` → **整个 workflow 解析失败**。而 `yaml.safe_load` 对重复键是**静默覆盖**，本地校验全绿也照样炸 | 合并成 `if: a && b`；彩排加**严格 loader** 静态体检（重复键 / step id / input 引用），并做负向测试 |
| 跨私有仓调 reusable workflow | 调用方 `GITHUB_TOKEN` 读不到另一个私有仓 → GitHub 统一报 `workflow was not found`（**伪装成 404**） | deploy-kit 仓改公开（仓内无凭证） |
| CI 报 `Unable to locate executable file: pnpm` | `actions/setup-node` 配了 `cache: pnpm` 之后，它会执行 `pnpm store path` 找缓存目录 —— 而**那时 pnpm 还没装**（装 pnpm 的步骤排在 setup-node 之后）→ `@actions/exec` 找不到可执行文件就抛这句 | 顺序铁律：**装 pnpm 必须在准备 Node 之前**（pnpm 官方文档给 setup-node 配缓存时要求的顺序）；彩排加顺序守卫断言（+3） |
| 发布日志刷 `no such service: worker` | 注册表里 `APP_SERVICES=""`（前端由 api 自己托管 → 只重建一次），但 releaser 那三个服务列表用的是 `:-` → **空串会回退成默认值** → 实际去重建本项目根本没有的服务。（`API_IMAGE` 早就用 `-` 做了「显式写空」的语义 ✓，服务列表没跟上 ✗） | 三个服务列表也改用 `-`（不是 `:-`）：显式写空 = 这一步不做，完全不写 = 用默认值；彩排加行为断言（+6） |
| 装第二个项目时**钥匙被共用** | 钥匙文件名写死 `deploy_ci_ed25519`（不带项目名）→ 第二个项目复用同一把私钥；且「已存在」只比**公钥**不比对**整条授权行** → **第二个项目的授权行根本没写进去**，而脚本**退出码 0**（静默失效）。后果：OpenSSH 只认第一条匹配公钥的授权行 → 第二个项目的 CI 被绑在**第一个项目**上（横向越权），且自己永远发布不了 | 钥匙**按项目分**（`deploy_ci_<项目>_ed25519`）；「已存在」改比**整条授权行**；重装同一项目时**沿用旧钥匙**（GitHub Secret 不用改）；彩排加「装两个项目」正反断言 |
| scp 没加 `-O` | **OpenSSH 9.0+ 的 scp 默认走 SFTP**（发的是 subsystem 请求），而 `authorized_keys` 的 `command="..."` 会**顶掉 subsystem 请求** → 受限入口脚本去接 SFTP 的活 → 客户端 `scp: Connection closed` | scp 强制老协议（`-O`，远程命令 = `scp -t <path>`），受限入口只认这一种 |
